# 用 Claude Code + Opus 开发一个可以对战的小游戏

这个项目从 PixiJS 五子棋开始，逐步补上 AI、好友对战、结算动画和账号存档。游戏主体和初版登录排行榜由 Claude Code / Opus 开发，移动端、部署与同步等后续工程问题由 Codex 继续迭代。以下是按当前代码整理的开发拆分方式和**可复用提示词示例**，不是逐字还原的原始聊天记录。

## 1. 先做能下完一局的规则层

先明确 15×15 棋盘、黑先、五子或以上获胜、无禁手、平局和认输。将规则放在独立 TypeScript 模块里，用测试覆盖越界、重复落子、横竖斜连线和结束后不能继续落子。规则正确后再让 PixiJS 绘制棋盘与棋子。

> 用 TypeScript 写一个与渲染无关的五子棋规则模块：15×15、黑先、五连或以上获胜、无禁手。给出落子、胜负判断、历史记录和悔棋接口，并测试四个方向、边界与非法落子。之后用 PixiJS 8 接入一个可玩的双人棋盘。

对应代码：`src/gomoku/rules.ts`、`src/ui/BoardView.ts`、`tests/rules.test.ts`。

## 2. 把 AI 和画面分开

三档 AI 复用棋型评分：简单档从候选点中带随机地选，中档同时权衡进攻和防守，困难档用 alpha-beta 迭代加深搜索。搜索放到 Web Worker，避免思考时卡住动画。AI 棋手是本地算法，不需要逐局调用模型 API。

> 在现有规则层上加入三档电脑棋手。简单档允许失误，中档优先必胜与必防，困难档使用有限时间的搜索。把计算放入 Web Worker，并处理悔棋或离开页面时旧搜索结果返回的问题。

对应代码：`src/gomoku/ai/`、`tests/ai.test.ts`。

## 3. 用房间号连接两个浏览器

在线房间使用 PeerJS / WebRTC。除了传坐标，还要检查落子序号和轮次、区分房主与访客、处理认输和重开。对手掉线或长时间无人加入时提供 AI 接手。公共信令服务用于建立连接，P2P 连通性仍受网络环境影响。

> 在现有五子棋中加入好友房间：房主创建 6 位房间号和邀请链接，访客加入后按轮次同步落子。验证落子顺序，处理重连失败、认输、颜色交换和再次对局；不要让房间故障阻塞本地玩法。

对应代码：`src/net/online.ts`、`src/popups/OnlinePopup.ts`、`tests/online.test.ts`。

## 4. 把动画当成独立功能

界面按 screens / popups / ui 分层。大部分素材用 SVG 描述，再转成 Pixi 纹理；GSAP 控制宝箱落下、升级、开盖、奖励卡出现与图标飞入 HUD。切换画面时销毁动画，防止回调继续访问已经销毁的 Pixi 对象。

> 为结算做一条清晰的动画时间线：宝箱落下、按表现升级、点击开箱、奖励展示、收下。允许跳过长动画；用户提前离开也只能发放一次奖励。统一紫金色、圆角按钮和描边字体，支持手机屏幕。

对应代码：`src/screens/ResultScreen.ts`、`src/result/`、`src/svg/`。

## 5. 最后接登录、排行与存档

游戏本身无需登录。邮箱验证码只用于查看排行和同步账号。排行榜积分由服务端复盘棋谱后计算；个人战绩与奖励通过独立事件同步。每个事件有稳定 UUID，服务端原子保存合计和回执，避免刷新、断网重试或多个设备一起上传时重复累计。

旧版只有汇总存档，没有每盘棋谱：保留历史胜负和奖励，并在榜单展示账号总胜负，但不凭空补算积分。这也是本项目后续实际修复过的边界。

> 不要给开局增加登录门槛。游客先保存在本机，登录后按账号归属上传。设计跨设备增量合并、稳定 ID 去重、响应丢失后重试、账号切换隔离和旧存档一次性迁移；保证个人战绩与排行榜展示一致，历史汇总不生成虚假的竞技积分。

对应代码：`server/`、`src/profile/`、`src/net/profileSync.ts`、`tests/leaderboard-progress.test.ts`。

## 6. 用可运行的验收代替“看起来完成了”

每轮只增加一组功能，运行 `npm test` 与 `npm run build`，然后用两个真实浏览器检查房间、移动端触控、退出登录和断网补传。Netlify 同时部署静态页面和 Functions，预览与正式存储分开；GitHub Actions 保持手动触发。

模型负责实现和迭代，人负责明确玩法、反馈体验并检查结果。这个仓库适合直接运行、阅读提交历史，再替换成自己的棋盘、素材或规则。
